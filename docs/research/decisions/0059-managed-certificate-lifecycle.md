# 0059: Managed certificate lifecycle

## Context

A device management service depends on certificate identities it cannot issue itself. Apple
issues the MDM vendor signing certificate and the customer APNs push certificate through
portals that require an interactive, authenticated human. HTTPS and device enrollment
identities are the operator's own, but they expire and must rotate without interrupting
enrolled devices.

These identities differ in who issues them, what depends on them and what a mistake costs,
yet they share one problem: private key material has to be created, stored, renewed and
replaced without being exposed, on any host the server runs on. Earlier practice generated
this material by hand with platform tools, which tied it to one machine's keychain and lost
it when that machine was rebuilt.

## Decision

`devicemanagement/pki/lifecycle` owns every managed identity. Four kinds share one model,
each named for what it is rather than for its position in the protocol:

| Kind | Issued by | What it does |
|---|---|---|
| `vendor-signing` | Apple Developer | Signs a customer's push certificate request |
| `mdm-push` | Apple Push Certificates Portal | Carries the topic that lets the server wake devices |
| `server-https` | The operator, or a public ACME CA | The server's own TLS identity |
| `enrollment-ca` | The operator | Issues device identities at enrollment |

The names are the wire values, the CLI verb groups, the admin route segments and the default
identity IDs, so one word identifies an identity everywhere an operator meets it. The
deployment `Setup.Role` keeps the separate values `vendor` and `customer`, which describe
which half of the signing exchange a deployment performs rather than a certificate.

### Keys are generated by the server, never by the platform

`generate` creates an RSA key and a CSR for each revision and seals the key in the
server's encrypted state as PKCS#8. Nothing reads a key from a platform keychain, and no
workflow accepts one. An operator runs the same commands on macOS and on Linux and gets the
same result, because the only inputs are the subject, the requested kind and the
certificate Apple or the operator returns.

### Identities are revisions, and the active one keeps serving

Each identity holds an ordered list of revisions. A revision moves through
`awaiting-certificate`, `ready`, `active` and `cancelled`. Preparing a new revision never
disturbs the active one: a renewal generates a *new* key and CSR alongside the identity
already in service, and the new material takes over only at activation, in one SQL
transaction. The runtime observes the version and reloads. HTTPS applies to new handshakes
while existing connections finish.

Two invariants protect enrolled devices. A push renewal must retain the exact APNs topic,
and any renewal must extend validity. A failed import or activation leaves the previous
identity active.

### Only public artifacts leave the server

`Export` serves `csr`, `signed-request` and `certificate`. There is no private-key export,
in the API or the library: the boundary is enforced by the type of artifact the exporter
understands, not by documentation. Listings and history carry public fingerprints, phases,
timing and actor attribution.

A customer deployment may delegate signing to a vendor deployment over HTTPS
(`setup.vendorUrl` with a credential permitted `signCustomerPushRequests`). Only the public
CSR crosses that boundary; the customer key stays in customer storage, and redirects cannot
forward the credential. Vendor signing re-reads the vendor identity under the lock so a
concurrent vendor renewal cannot sign with material that is being replaced.

### Apple's authorities are pinned, not fetched

`devicemanagement/pki/lifecycle/apple` embeds Apple's public root and intermediate
certificates with their official download URLs, DER SHA-256 digests and a review date. The
importer completes Apple's issuer chain from that bundle and verifies key pairing, validity,
signing purpose, chain order and trust anchor. The legacy Apple root's SHA-1 self-signature
is not revalidated as an issued certificate; signatures of issued chain members still
undergo normal verification. Pinning keeps verification identical on a developer's Mac and
in Linux CI, with no network fetch in the trust path.

### Renewal is scheduled, and its urgency is recorded

The worker derives `RenewAt` from the active revision: 60 days before expiry for push and
vendor identities, 180 for issuers, at most 30 for HTTPS, and no more than one third of a
short certificate's lifetime. It records persistent notices once per revision and threshold,
escalating through `renewal-due`, `expires-in-30-days`, `14`, `7`, `1`, `0` and `expired`,
and reports the next action to run. `setup check` fails while a required certificate is
missing or expired, so a deployment cannot quietly run past its own expiry.

### The portal steps are attended, deliberately

Apple's vendor and push portals require an interactive sign-in with two-factor
authentication and publish no API for issuance. The server prepares the exact artifact to
upload and validates what comes back, and the operator performs the portal step. Automating
that sign-in is out of scope: it would require handling an Apple account credential, it
breaches the terms those portals are used under, and it would break whenever the pages
change. Tooling around the step is automated; the step itself is a checkpoint.

### Losing a key means reissuing, not recovering

A private key that is gone cannot be recovered, and no workflow pretends otherwise. What
the lifecycle guarantees instead is that reissuing is cheap and non-destructive:

- **Push identity:** request or renew produces a fresh key and CSR, and Apple's portal
  renewal returns a certificate for the same topic. Because devices identify the service by
  topic rather than by key, enrolled devices keep working across the replacement.
- **Vendor identity:** no topic depends on it, so a lost vendor key is replaced by a new
  request and a new Apple Developer issuance. Previously signed customer certificates stay
  valid.
- **HTTPS and issuer identities:** replaced through the same revision model, with issuer
  replacement driven by the rollover cohort so enrolled devices migrate before the old CA
  is retired.

Surviving the loss of a *host* is a separate mechanism: `server/recovery` writes an
authenticated, encrypted checkpoint containing a consistent SQL snapshot, the setup
configuration and the original storage keys, verifies it, and restores it into an empty
deployment that stays paused until an operator resumes writes. That, not key export, is how
key material is carried off a machine.

## Rationale

The kinds are named for the identity rather than for the mechanism that carries it, because
the audience is an administrator deciding which certificate is missing, not a reader of the
protocol. `push` did not say whose push or why it mattered, `https` and `issuer` did not say
whose, and `vendor` collided with the deployment role of the same name. Reusing one word as
the wire value, the CLI group, the route segment and the default identity ID means an
operator learns each name once.

One model for four kinds keeps the operator's mental model and the code paths small: the
same request, sign, import, activate and renew verbs apply whether Apple or the operator
issues the certificate. Generating keys in the server rather than with platform tools is
what makes the workflow portable and reproducible, and it removes the class of failure where
an identity exists but its key is bound to a keychain on a machine that no longer exists.

Refusing private-key export is the decision that makes the rest safe to automate. An export
path would be used routinely for convenience, and every copy would then have to be tracked,
so the sealed store would stop being the boundary it claims to be. Backup and restore covers
the legitimate need with an explicit pause, verification and an empty destination.

Pinning Apple's authorities trades a periodic review for deterministic verification. The
alternative, reading the host trust store, would make macOS and Linux behave differently on
the same input and would place a platform dependency inside certificate verification.

Scheduling renewal on a lead time proportional to the certificate's own lifetime, and
recording escalating notices, addresses the failure that actually happens: nobody notices an
expiry until devices stop responding.

## Constraints

The kind names are stored inside each identity record and its history, and the state store
has no value-level migration. A deployment created before this vocabulary therefore keeps
records the current validation rejects, and its identities must be requested again; for the
push identity that means Apple's portal once more, choosing **Renew** so the topic survives.
The names also appear in `server.certificate.lifecycle` webhook payloads and in audit action
strings, so consumers of either see the new values.

Apple's portals gate both the vendor and push identities on an interactive human, so no
deployment reaches a working MDM push identity unattended. A push certificate lasts one
year; the topic must be retained across renewals or enrolled devices stop accepting the
service. Storage keys must be retained with the database they seal, since sealed material is
unreadable without them. Restored deployments hold their write pause until an operator
resumes them, and the original processes must be stopped first. A revision that is pending
must be cancelled before another can be prepared for the same identity.

## Verification

- `devicemanagement/pki/lifecycle`: contract tests for each kind's request, sign, import,
  activate, cancel, export and renewal paths, including topic retention, validity
  extension, chain completion from the pinned authorities and concurrent renewal under lock.
- `server/internal/app`: setup workflow and status contracts, renewal scheduling and notice
  thresholds, and the failure paths that leave the previous identity active.
- `server/recovery`: checkpoint creation, verification and restoration into an empty
  deployment.
- `dmctl setup status`, `setup check` and `setup workflow show|history` report the state an
  operator acts on; `check` fails while a required certificate is missing or expired.
